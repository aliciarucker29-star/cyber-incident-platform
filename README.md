\# Automated Cyber Incident Investigation Platform



\## Overview



The Automated Cyber Incident Investigation Platform is a senior capstone project designed to automate key stages of cybersecurity incident investigation.



The platform ingests security event data, stores it in PostgreSQL, analyzes events using a C++ investigation engine, correlates related detections into incidents, constructs investigation timelines, extracts indicators of compromise, calculates transparent risk scores, maps supported behavior to MITRE ATT\&CK techniques, and presents investigation results through a React dashboard.



An AI-assisted investigation component generates evidence-grounded summaries and recommended investigation steps. The AI is used to explain and summarize existing evidence rather than acting as the primary detection authority.

\## Core Features



\### Security Event Ingestion



The FastAPI backend supports ingestion of individual security events and batches of events.



Input validation rejects incomplete or malformed events before they are stored.



\### PostgreSQL Storage



Security events are persisted in PostgreSQL and can be retrieved or exported for investigation processing.



Database credentials are loaded through environment variables rather than being hardcoded in application source code.



\### C++ Detection Engine



The investigation engine analyzes exported security events using deterministic detection logic.



Implemented authentication detections include:



\- Repeated authentication failures

\- Failed authentication followed by successful authentication



The repeated authentication failure rule triggers when five or more failed authentication attempts occur within a ten-minute window.



\### Incident Correlation



Related detections are correlated into incidents using common evidence such as:



\- Username

\- Hostname

\- Source IP address

\- Related event IDs



\### Investigation Timeline



Evidence associated with an incident is organized chronologically to provide analysts with a clear sequence of activity.



Timeline entries include information such as:



\- Timestamp

\- Event ID

\- Action

\- Username

\- Source IP

\- Hostname

\- Description



\### Indicator Extraction and Enrichment



The investigation engine extracts indicators from incident evidence.



Current indicator processing includes IP address extraction and classification.



Private IP addresses are identified separately from public addresses. Public IP addresses that have not been checked against an external reputation source are explicitly marked as having unknown reputation.



\### Transparent Risk Scoring



Risk scores are calculated using explainable rules rather than AI-generated severity decisions.



Examples of risk factors include:



\- High-severity incident evidence

\- Multiple correlated detection rules

\- Failed authentication followed by successful authentication

\- Public IP address involvement



Each incident includes both a numeric risk score and the reasons contributing to that score.



\### MITRE ATT\&CK Mapping



MITRE ATT\&CK techniques are mapped only when supported by observed evidence.



Current mappings include:



\- T1110.001 — Password Guessing

\- T1078 — Valid Accounts



Technique mappings include confidence and reasoning to avoid presenting uncertain activity as confirmed compromise.



\### AI-Assisted Investigation



The AI investigation component uses structured incident evidence generated by the investigation engine.



It can summarize:



\- Observed activity

\- Timeline evidence

\- Indicators

\- Risk assessment

\- MITRE ATT\&CK mappings

\- Investigation uncertainty

\- Recommended next steps



The AI component is not the detection authority. Detection, correlation, and risk scoring are performed before the AI layer receives the incident data.



\### React Investigation Dashboard



The dashboard provides a visual interface for reviewing incidents.



It displays:



\- Total incidents

\- High-risk incidents

\- Indicators

\- Investigation engine status

\- Incident cards

\- Risk scores

\- Risk reasons

\- Indicators

\- MITRE ATT\&CK mappings

\- Investigation timelines

\- AI-generated investigation summaries

\## Backend Setup



Navigate to the backend directory:




Create and activate a Python virtual environment if needed, then install dependencies:

\## C++ Investigation Engine



Navigate to:



```cmd

cd investigation-engine

```



Build the engine:



```cmd

cmake --build build --config Debug

```



Export the latest events from FastAPI:



```cmd

curl http://127.0.0.1:8000/events/export -o events.json

```



Run the investigation engine:



```cmd

build\\Debug\\investigation\_engine.exe

```



The engine writes investigation results to:



```text

investigation\_results.json

```



The FastAPI investigation endpoints expose these results to the frontend.

\### Detection Threshold Evaluation



A controlled threshold test was performed against the repeated authentication failure rule.



Sub-threshold authentication failures did not generate an incident.



Exactly five failed authentication attempts within ten minutes triggered the expected repeated-authentication-failure detection and produced a correlated incident.



This test demonstrated that the engine applies its configured detection threshold rather than generating an incident for every authentication failure.



\## Security Considerations



The platform incorporates several security-oriented design decisions:



\- Database passwords are not hardcoded in application source code.

\- OpenAI API credentials are not hardcoded in application source code.

\- Credentials are loaded from environment configuration.

\- `.env` is excluded from source control.

\- FastAPI validates incoming event structures.

\- AI output does not replace deterministic detection logic.

\- Risk-score reasons are retained for explainability.

\- MITRE ATT\&CK mappings include supporting reasoning.

\- Unknown indicator reputation is not presented as malicious.

\- Investigation conclusions distinguish observed evidence from uncertainty.



\## Current Scope and Limitations



This project is a capstone-scale investigation platform rather than a production SIEM.



Current limitations include:



\- A focused set of authentication detection rules

\- File-based exchange of investigation results between the C++ engine and backend

\- Limited IOC enrichment

\- Local development deployment

\- No distributed event-processing infrastructure

\- No malware sandboxing

\- No automated containment or remediation



These limitations intentionally keep the project focused on demonstrating incident ingestion, detection, correlation, investigation, explainability, and AI-assisted analysis.

\## Capstone Objective



The primary objective of this project is to demonstrate how deterministic security analytics, structured incident correlation, explainable risk scoring, and evidence-grounded AI assistance can be combined into a unified cyber incident investigation workflow.



The resulting platform demonstrates an end-to-end pipeline from raw security events to analyst-facing investigation results while preserving transparency about how detections and risk assessments were produced.
